# Meiva — Knowledge Graph

Root node of the Meiva project's OKF (Open Knowledge Format) knowledge graph. Each package keeps its `.meiva.okf.md` concept files in its own `docs/` directory, beside the source code they describe — the hierarchy comes from the file system, with the `docs/` layer transparent: `<dir>/<dir>.meiva.okf.md` (logical path) is the overview node for directory `<dir>/`, the other files inside `<dir>/` are its child concepts, and this file is the root node of the entire graph.

**A package's nodes live in its `docs/` layer.** Every domain overview node belongs to the directory it describes — its logical path is `agent/agent.meiva.okf.md` for `agent/`, `agent/graph/graph.meiva.okf.md` for `agent/graph/` (user ruling: "put it inside the folder", not beside it at the parent level). The `docs/` layer is transparent to the hierarchy: `base/packages/docs/okf_graph.py:logical_path()` drops the last `docs` directory segment of a path, so `agent/graph/docs/graph.meiva.okf.md` sits at `agent/graph/graph.meiva.okf.md`. `compute_parent()` resolves the hierarchy on logical paths: a file's parent is its nearest ancestor directory's overview (logically `a/b/c.meiva.okf.md` → `a/b/b.meiva.okf.md`; on disk `a/b/docs/c.meiva.okf.md` → `a/b/docs/b.meiva.okf.md`), returned as that node's physical path. Links are not logical — wikilinks and relative markdown links name the real path, `docs/` included. `compute_parent` does not resolve a sibling overview (`a/b.meiva.okf.md` beside `a/b/`), and lint rule E009 reports one, layered or not. This apex and the cross-domain plugin, skill and MCP concept systems live in the repository's `docs/` layer because they have no single code directory to own them. Chosen alternatives and their rationale use ordinary Markdown in `docs/decisions/`; unimplemented proposals and plans use ordinary Markdown in `future/`. Overview nodes skip themselves and search enclosing directories; directories without overviews are skipped. Nodes without any ancestor overview attach to this root; parents are only ever returned if they exist, so the tree has exactly one root and no dangling edges.

## Generation method

Each concept file is written by an agent after reading the corresponding source code — not automatically generated by scripts. The graph is built **on demand by the gateway**: `GET /api/okf/graph` (`gateway/inspect/okf_graph.py`) calls `base/packages/docs/okf_graph.py:build_graph_data()` per request and renders the D3 visualization from `scripts/codegen/okf-d3-template.html`. `scripts/codegen/build_okf_data.py` is a CLI wrapper over the same builder (for offline builds / viz serving); there is no checked-in `graph_data.json`.

## Update method

Meiva code changes → agent reviews changes → updates affected concept files → `scripts/content_lint/lint_meiva_okf.py` validates (the gateway rebuilds the graph live, so no separate rebuild step) → `scripts/content_lint/check_doc_references.py` for markdown-link drift.
