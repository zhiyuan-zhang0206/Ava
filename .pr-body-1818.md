## What / Why

Fresh split agent-runners without a configured memory remote silently got a stub local pool, and their agents saw no shared memory — **company-mini / agent 3702, 2026-08-27** (headless `ava enroll`: no TTY to answer the `memory_remote` prompt, and no `gh` CLI / GitHub key on the box, so the steward->PR->arbiter sync path can never run).

Fix per 405's ruling (user principle of one endpoint + credential access model, applied to the memory pool): the **gateway serves the consolidated pool**; a no-remote split runner **bootstraps from the gateway** instead of birthing a stub; the silent stub path becomes a **loud failure**.

## Data flow

```
fresh split runner, no memory_remote
  ava start -> converge -> ava_memory scaffold -> memory_repo.init()
    |- gateway-capable unit (single-box fresh install): local init, unchanged
    |- split agent-runner:
         GET {gateway_url}/api/memory/pool  (Bearer cluster secret)
           -> gateway: tar.gz of gateway_memory_dir() (consolidated main checkout)
         extract (filter="data") -> git init machine-<name> + snapshot base commit
         on fetch/extract failure -> MemoryRemoteMissing (loud; guidance in message)
```

- `AVA_MEMORY_KEEP_LOCAL` still opts out entirely (checked before the bootstrap branch).
- The endpoint sits behind the normal `/api` Bearer/session middleware — no new auth surface.
- Existing machines (mba/win/wsl have `memory_remote` files; already-initialized pools) are untouched: `init()` only bootstraps a missing checkout.
