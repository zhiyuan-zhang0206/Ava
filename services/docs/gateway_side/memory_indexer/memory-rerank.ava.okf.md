# Memory Search Read Path

- **Retrieval**: `search_topk` retrieves the top-200 raw chunk hits, aggregates per path (best cosine wins) and returns the top-k files as `ChunkHit(path, kind, chunk_idx, score)` — the winning row's coordinates and its cosine similarity. The gateway asks for the purpose's candidate count (`memory_rerank_candidates`, default 30) plus the number of paths the request excludes, whatever `k` is.
- **Exclusion and the candidate cap**: the request's `exclude` list (memory-pool-relative paths, at most 800, each normalized: no leading slash, no `.`/`..`/empty segment, no control character; anything else is a 422) is applied in `rerank._load_candidates` before a file is read, and the first `memory_rerank_candidates` (`memory_dedup_candidates` for `dedup`) surviving hits are the candidates. An excluded, stale or unreadable hit takes no slot. `k` only truncates the ranked list, so `k` above the candidate count returns at most the candidates: the decision requests of one search are fixed by configuration, not by its arguments.
- **Chunk text**: the index stores vectors, not text. The gateway reads the note file and restores the row with `chunking.chunk_text`, which applies the indexer's own split rules. A hit whose file is gone, unreadable or no longer produces that row (the index lags the pool) is dropped before ranking.
- **Ranking**: `rerank.py` makes one decision request per candidate, concurrently (at most 30 in flight, so a default search sends all of them together). The state is the query plus that one note (path, description, excerpt of at most 1800 characters); the single yes/no question asks whether the note is worth the agent reading. `purpose` on the request picks the wording: `recall` (the query is the recent conversation), `search` (an agent's own query) or `dedup` (the query is a note an agent has just written, and the question asks whether the candidate records essentially the same knowledge; its threshold, `memory_write_dedup_threshold`, is not benchmark-calibrated). Results are ordered by the probability of yes, ties keeping vector order. No text is generated.
- **Calibration**: the passive-recall threshold is a probability from this exact model (`jev-1.13.0`) and these exact templates, calibrated by the 2026-10-11 benchmark. The wording lives only in `rerank.py`; changing the model, a question or a state template means recalibrating `memory_recall_inject_threshold`.
- **Cost and depth**: a search issues up to `memory_rerank_candidates` (30) decision requests, however large its `k` or its exclusion list (`memory_dedup_candidates`, default 5, for the `dedup` purpose). The 2026-10-11 benchmark found 30 candidates as good as 50 for passive-recall precision at the 0.80 threshold (P(≥1) about 0.77) and nearly so for search (nDCG@5 0.746 against 0.755), at about 60% of the cost; with every request in flight the ranking took about 2s for 30 candidates and about 3s for 50.
- **Failure**: a failed decision call fails the search as `IndexerUnavailable` (wire 503) naming the model and the cause, and the gateway logs a warning. There is no fallback to cosine order: a silent downgrade would hide a broken ranking behind plausible-looking results. The whole request shares `memory_search_deadline_seconds` (a request's `deadline_seconds` can shorten it, never lengthen it); the rerank runs outside the query-embed concurrency gate. Nothing keeps the ranking alive once nobody waits: the handler races the search against the client disconnecting (`gateway/http/disconnect.py:run_until_disconnect`) and against the deadline, and cancelling it cancels the task group of in-flight decision requests, so the unanswered ones stop and are not billed. A caller that stops waiting on its own clock must also say so in `deadline_seconds`, because a blocking client call cannot be interrupted and so never closes its connection (passive recall does).
- **Usage**: each decision call writes one `llm_usage` row with `usage_kind=memory_rerank` (`memory_write_dedup` for the `dedup` purpose).
