Part one

Executive summary

By mid-2026 the frontier agents split into two camps, and a third has just opened. Terminal coding agents (Claude Code, Codex, opencode, Grok Build, Kimi Code, pi) optimize a developer's session: open a terminal, finish the task, close it. Always-on personal agents (Ava, OpenClaw, Hermes) optimize persistence and reachability: the agent lives as a daemon on your own hardware and reaches you over messaging channels. On 2026-08-13 DeepSeek opened the third camp with DeepSeek Harness (dsh, v0.1 developer preview, MIT, 35.5k stars on day one): a web-first, session-scoped harness platform built on a vendored Cordis kernel where even the agent loop, the tool registry, and the session log are plugins — "an open harness that runs anyone's model is a bid to own the workspace rather than the engine."

The coding camp's primary action model has homogenized on multi-tool dispatch — but the quieter trend went louder in the last two weeks: code-as-action is becoming the industry's optional mode. DeepSeek Harness ships a first-class Code Mode switch (native | code | both): under code the wire carries a single run_code transport plus a generated TypeScript/Python SDK, so the model composes tools inside one program — worker-thread isolated, bounded-parallel dispatch — while its Standard mode is the same multi-tool dispatch as the rest of the camp. opencode's CodeMode tool (confined JavaScript over schema-described tools, landed 2026-07-02) is now flag-gated experimental in the shipping CLI. Codex hides an experimental Code Mode subsystem in source (OpenAI can even enable it server-side per model), OpenClaw's Code Mode defaults to auto, and Hermes ships execute_code on by default (bounded tool coverage). All ten implement the Agent Skills open standard (SKILL.md + YAML frontmatter); all but pi — which rejects it deliberately — speak MCP. With the extension standards converging, competition moved elsewhere: ecosystem absorption (Grok Build reads Claude Code's skills, plugins and MCP config with zero configuration; DeepSeek Harness delegates subagent tasks to real Claude Code and Codex processes), scale (Kimi's built-in swarms fan out to 300 sub-agents), and openness (opencode's ~190k-star fully open stack against Claude Code's closed distribution).

The personal-agent camp competes on channels and persistence: OpenClaw claims 29+ channels, Hermes fronts ~20 platforms behind one gateway. But both stop their self-evolution at the skill-and-memory layer — the agent can write its own SKILL.md, not upgrade its own runtime. DeepSeek Harness is the only other product that lets the agent touch its own runtime mid-session (cordis_inspect / cordis_mount / cordis_unmount mount model-written temporary plugins into the live process — opt-in, bash-equivalent trust) — but it ships no self-update of its installed code.

Across this 150-cell matrix, Ava holds three cells alone: the only product whose sole action model is code-as-action (one tool, execute_code; every capability is a Python call under ava.* — where others bolt on code-act as an escape hatch, Ava makes it the whole interface), the only one that makes cluster-wide self-upgrade a single operator command (ava cluster update: drain live agents → pull → migrate the database → restart; the ava.self.update() SDK call that previously held this cell was removed 2026-08), and the only verified yes on the observability row (an LGTM-class stack — OTel + Tempo + Loki + Prometheus + Grafana — with a local trace mirror and an agent-callable trace toolchain). Running on DeepSeek-V4, the production cluster measures a 99.36% input-token cache hit rate (36.4B input tokens over 262,757 calls; the 口径 is in Ava's model-routing cell). The costs sit in the same matrix, honestly: no runtime sandbox, a web-console-only UI, a goal mode shipped but not yet exercised, a young ecosystem.

Credibility statement: every cell rests on primary sources the research agents opened themselves. Eight adversarial verification groups re-checked 85 cells and produced 5 corrections; a reader-challenge round re-verified 4 contested cells and produced 2 further rating changes plus 5 addenda — all marked in place. Of the ten products' single most load-bearing differentiator claims, zero were refuted. DeepSeek Harness was researched live on its launch day (2026-08-13) — the repo cloned and read (AGENTS.md, architecture, generated tool catalog, 219 workspace packages), plus the official page, npm, the HN launch thread and press coverage; every dsh cell cites a repo file or a dated press source. Ava

Code-as-action fleet: one tool, a persistent self-hosted multi-agent cluster

Identity & status

Ava is a local, self-hostable, code-as-action multi-agent framework matching the hint exactly: a single execute_code(code: str) tool plus one ava.* SDK namespace provide all capabilities (README.md, CLAUDE.md). It runs on LangGraph's two-node (llm/exec) execution graph per agent process, and every deployment ("cluster") owns its own native Postgres 17 + Redis 8.8 data plane under its own $AVA_HOME — no shared/managed infra. Its headline differentiators are "Fleet Mode" (peer-to-peer multi-agent spawn/fork/message, no central scheduler) and self-evolution (agents can modify Ava's own source and ship it cluster-wide via ava cluster update (the CLI; the removed ava.self.update() SDK call previously held this role) after PR→CI→merge). It is pre-1.0, Apache-2.0 licensed, source-available in this local checkout.

As read from the local repo on 2026-07-28: CHANGELOG's [Unreleased] section shows recent additions of "open-source readiness" (Apache-2.0 license, community-health files, forkable CI) and a China-mirror install flag; project explicitly labeled pre-1.0. Docker/container-based per-agent sandboxing is roadmap-only (future/roadmap/docker-sandbox.md), not shipped. Passive memory recall is present but disabled by default (experimental).

Positioning

Ava sits at the maximalist end of the code-as-action lineage (CodeAct / smolagents / Claude Code style code execution) but scaled from "one agent that writes code" to "a persistent, self-hosted fleet that writes code, spawns peers, and rewrites its own instructions" — closer to an always-on personal/team agent operating system than to an SDK you import into an app. It is aimed at an operator-owner who will run their own Postgres/Redis on their own boxes and wants full source access and no vendor data plane, and who is comfortable trading sandboxing for capability today: agents run on the bare host. Its bet is that as models get stronger, scaffolding is a liability — so the winning framework is the one with the smallest core (one tool, one namespace, markdown skills), and its second bet is that decentralized peer-to-peer agent graphs plus a PR→CI→merge self-update loop beat centrally-scheduled, statically-declared workflow DAGs.

In depth

Ava is a self-hosted, Apache-2.0 CodeAct multi-agent system built on LangGraph, whose defining constraint is that agents get exactly one tool — `execute_code(code: str)` — and reach every capability as a Python function under the single `ava.*` namespace, deliberately rejecting multi-tool dispatch and JSON-schema tool calling on expressiveness and escaping grounds. Each agent is one OS process running one LangGraph thread on a claim→llm→exec→claim loop, with three plugin hook containers (before_llm / before_exec / after_exec) as the framework's extension seams. Multi-agent is native rather than layered: `ava.agents.spawn` / `fork_from` / `send_message` / `get_neighbors` form a decaying peer graph with no central scheduler, and because spawned agents are detached OS processes (optionally on another machine), parallelism is real and decomposition is decided at runtime by the model writing an orchestrator script. Extension has three tiers — markdown skills (~21 built in, lazily loaded, installable from git, agent-authorable via `skill_creator`), Python plugins with state/prompt/SDK-namespace injection, and MCP client integration (`ava.mcps.<server>.<tool>`, built-in Chrome, others via `ava mcp install`). Self-evolution is genuine but gated: agents edit Ava's own source, but changes only reach the cluster through dev-clone → PR → CI → human merge → `ava cluster update` (the CLI; the `ava.self.update()` SDK call was removed 2026-08), which drains every agent, pulls `main`, migrates the DB and respawns the fleet on the new code; a separate weekly `ava_self_evolution` cron mines real run traces and rewrites skill text. Multi-model routing is a first-class per-agent capability: eight provider families and ~26 model ids in one registry, routed by `config_overlay={"llm_model": ...}` or named presets, validated at the spawn boundary. Long-running work is served by `ava.watcher` (at/cron/launch), gateway-supervised schedules with restart + circuit breaker, and a heartbeat/hibernation daemon pair, with `pause_heartbeat` as the explicit anti-idle verb. The data plane is entirely operator-owned — every cluster runs its own native Postgres 17 + Redis 8.8 under its `$AVA_HOME` with always-on cluster-secret auth and loopback-only-by-default binding. The clearest gap is isolation: `execute_code` runs directly in the agent process and `ava.shell` spawns onto the bare host, so the permission story today is an example `before_exec` hook under `demos/` plus a best-effort injection scanner, with a containerized disposable cluster still on the roadmap.

MCP● yes

Ava is an MCP **client** only — agents call `ava.mcps.<server>.<tool>(**kwargs)`, which serializes to newline-delimited JSON over a Unix socket to a per-agent MCP daemon subprocess; standard JSON-RPC is spoken only on the daemon↔server hop. Only `chrome` ships built in; X is documented as installed via `ava mcp install <repo-url> --env ...`. I found no evidence Ava exposes itself as an MCP server, hence 'partial'. Multi-agent● yes

Multi-agent is the core primitive, not a layer: `ava.agents.spawn(prompt=..., fork_from=..., machine=..., config_overlay=..., preset=...)` returns an agent id without blocking, plus `send_message` / `terminate` / `resurrect` / `get_neighbors(depth=)` / `get_status`. Parallelism is genuine OS-level — each agent is a separate detached process (reparented to init, not a child of its spawner) with its own LangGraph thread, so one crashing does not affect others, and agents can be placed on a different machine via `machine=`. Decomposition happens at runtime inside `execute_code`: the `ava_dynamic_workflow` skill's explore→fork→join→reduce pattern is just a Python orchestrator script the agent writes in its turn — 'no YAML pipelines, no DAG configs, no external scheduler'. Ties form on spawn/fork/resurrect/message and decay, so peer discovery is graph-based rather than hierarchical. The fleet's weight extends past the process graph: ava.ui.notify() gives every agent a user-facing notice queue (P0–P3, require_response / blocking, one open notice per agent, auto-supersede, dismiss/edit), served to Telegram through the IM bridge reading the agent_notices table; and ava.tasks is a shared persistent task registry — parent/child task trees, ownership, priority, and per-owner reminder intervals — so coordination outlives any single agent. Two honest notes: the label= argument shown in the README is added by the ava_fleet plugin's _spawn_with_label monkeypatch, not core spawn; and the demo table's scale figures (40 agents/7 waves deep research, 28 agents/7 waves codebase sweep) are demo prompts, not benchmarked guarantees.

Dynamic workflow● yes

Ava meets the bar through the same property that defines the product: it is a code-act agent whose only tool is `execute_code`, so `ava.agents.spawn()` and `ava.agents.send_message()` are ordinary Python calls and an orchestrator can write and run a full orchestration program inside a single turn. The `ava_dynamic_workflow` skill formalizes this as explore → fork → join → reduce: the LLM decomposes the task at runtime, spawns one worker agent per sub-task with a self-contained prompt, joins via a watcher that wakes it when all handoff files land (explicitly forbidding polling loops), then reduces the results. Parallelism is process-level across separate agent processes rather than threads inside one, and the pattern nests — a worker can itself be an orchestrator.

Goal mode◐ partial

Ava's `ava_goal` skill implements goal mode as a two-agent evaluator-optimizer: a supervising agent launches a one-shot watcher on a target agent, goes idle, and is woken the moment the target idles, at which point it inspects the target's actual output and either declares the goal met or states exactly what is missing and re-arms a fresh watcher. Its distinguishing property against the other nine is that the supervisor is a full peer agent with its own tools — it can read the artifact, run checks, and query status rather than only reading a transcript — and the skill instructs it to judge the artifact, never the worker's own claim of completion. Notably it also scopes itself: goal mode is for terminal work, and putting a perpetual trigger-driven agent under it is called out as harassment.

OpenClaw is the current name (since Jan 30, 2026) of the open-source, self-hosted personal AI assistant originally launched by Peter Steinberger as "Clawdbot" in Nov 2025, briefly renamed "Moltbot" (Jan 27, 2026) after an Anthropic trademark complaint, then renamed again three days later to "OpenClaw." Positioning

OpenClaw sits at the "ambient personal agent" end of the landscape — where Claude Code, Codex and Devin optimize a developer's terminal loop, OpenClaw optimizes reachability: the agent lives on your own hardware as a daemon and meets you in whatever chat app you already use, on phone, desktop or voice. Its audience is technically-capable power users and self-hosters who want one always-on assistant with real system access (shell, files, browser, calendar, email) rather than a sandboxed SaaS chatbot, and who accept operational burden in exchange for owning the data plane outright. The bet is that distribution through existing messaging surfaces plus a community skill marketplace beats a polished first-party client — a bet that has produced extraordinary adoption and, in ClawHub's malware incidents, an equally instructive lesson about agentic supply-chain risk.

In depth

OpenClaw is a self-hosted, MIT-licensed personal AI assistant built around a single local Gateway daemon that owns messaging channels, sessions, tools and events, exposed over a WebSocket API on port 18789. It began as Peter Steinberger's Clawdbot in Nov 2025, was renamed Moltbot after an Anthropic trademark complaint, then OpenClaw on 2026-01-30, and is now stewarded by the non-profit OpenClaw Foundation; the repo currently sits at 384k stars, 80.8k forks and 73,105 commits, with latest release v2026.7.1 (2026-07-13) credited to 532 contributors. Its defining bet is messaging-first ubiquity: 29+ channels, of which only iMessage, Telegram and WebChat are core and the rest — Discord, Slack, WhatsApp, Signal, Teams, Matrix, IRC, LINE, Feishu, SMS via Twilio, voice calls via Plivo/Telnyx/Twilio — are official plugins. The agent runtime is multi-tool dispatch by default (`exec`, `read`, `write`, `browser`, `cron`, `sessions_*`, media tools) but ships an experimental Code Mode that flips it into code-as-action, hiding the tool catalog behind `tools.search/describe/callValue` inside a QuickJS-WASI sandbox — and Swarm builds on that to let one program fan out to parallel sub-agents via `Promise.all`. Memory is deliberately file-first and auditable (`MEMORY.md`, `USER.md`, dated `memory/YYYY-MM-DD.md`, `SOUL.md`), now with hybrid vector+keyword `memory_search` and a background "Dreaming" consolidation that promotes daily notes into long-term memory. Automation is genuinely deep: a Gateway-resident cron scheduler with one-shot/interval/cron/on-exit/stream-command triggers, a background Tasks ledger, heartbeats, standing orders and webhooks. Security is layered and honest about its limits — sandbox (default `off`), tool policy enforced before the model call, and a separate elevated escape hatch — but the ClawHub skill registry has been the project's real weak point, with 341 malicious skills (~12% of the registry) found in Feb 2026 and evasive ones still slipping past VirusTotal/ClawScan as late as May 2026. Surfaces span CLI, browser Control UI, macOS/Windows desktop apps, iOS/Android nodes with voice, and agent-rendered HTML widgets.

OpenClaw is a multi-tool-dispatch agent by default, not single-tool code-as-action: a Gateway daemon (default port 18789) owns channels, sessions, tools and events, and the embedded agent runner (`src/agents/embedded-agent-runner/`) runs an attempt loop of intake → context assembly → model inference → tool execution → streaming → persistence, exposing dozens of named tools (`exec`, `read`, `write`, `edit`, `apply_patch`, `process`, `browser`, `message`, `cron`, `sessions_*`, `image_generate`, …). The maximalist single-vendor harness — richest product layer in the field

Identity & status

Claude Code is Anthropic's official agentic coding tool/CLI, confirmed live at code.claude.com/docs with source now public at github.com/anthropics/claude-code (opened March 31, 2026). It runs in terminal, IDE extensions, a desktop app, and web, and matches the hint exactly: skills, MCP client+server, subagents/agent teams, hooks, sandboxing. Positioning

Claude Code sits at the maximalist end of the single-vendor agent-harness landscape: it bets that the harness should be a rich, opinionated product layer — permission modes, sandboxes, checkpoints, four orchestration tiers, chat channels, artifacts — rather than a thin loop that gets stripped as models improve. It targets professional and enterprise engineering teams who want an agent that works everywhere they already are (terminal, IDE, desktop, browser, phone, Slack, CI) with MDM-grade governance, and who accept Anthropic-hosted inference as the trust boundary in exchange. Its structural trade-off against open, self-hostable, code-as-action agents is stark: the extension surface (skills, MCP, hooks, plugins, workflows) is fully open and portable, while the engine, the models, and the data plane are not — you can reshape everything around the loop but never own or fork the loop itself.

In depth

Claude Code is Anthropic's first-party agentic coding harness, at v2.1.220 as of late July 2026, shipping as a proprietary native binary across terminal, VS Code/Cursor, JetBrains, a desktop app, the web at claude.ai/code, and the Claude mobile apps — all driving one shared engine and config. Its architecture is classic multi-tool dispatch (Read/Edit/Write/Bash/Grep/Glob/WebFetch/LSP plus orchestration tools), not single-tool code-as-action, wrapped in an agentic loop with automatic compaction, file checkpoints, and JSONL session transcripts. The extension layer is unusually complete and well-factored: CLAUDE.md and path-scoped `.claude/rules/` for always-on context, `SKILL.md` skills (Agent Skills open standard) for on-demand knowledge, MCP for external tools, hooks for deterministic enforcement, and plugins/marketplaces as the packaging tier — with an explicit context-cost table for each. Multi-agent support spans four tiers: in-process subagents (background by default, nestable to depth 3), experimental agent teams of peer sessions with a file-locked shared task list and JSON mailboxes, dynamic workflows where Claude writes a JavaScript orchestration script that runs up to 1,000 agents out-of-context, and daemon-hosted background agents that survive terminal close and auto-isolate into git worktrees. Memory is genuinely two-sided: human-authored CLAUDE.md layers plus Claude-authored auto memory under `~/.claude/projects/<project>/memory/` with a 200-line/25KB index budget. Security is the most rigorous in the category — OS-level Seatbelt/bubblewrap sandboxing with proxy-enforced domain allowlists, credential masking through a TLS-terminating proxy, and MDM-deployable managed settings — and the docs are candid about the remaining holes (no default TLS inspection, Apple Events, weaker nested sandboxes). Scheduling spans session-scoped `/loop` cron, local Desktop tasks, and Anthropic-hosted Routines; Channels push Telegram/Discord/iMessage events (and remote permission approvals) into a live session. The critical correction to the common misreading: the GitHub repo holds only plugins, examples, and a changelog — LICENSE.md is "© Anthropic PBC. All rights reserved," the CLI source is closed, and no part of the stack is self-hostable.

Security● yes

Six layers. (1) Permission rules (allow/ask/deny) evaluated per tool call before execution across Bash, Read, Edit, WebFetch and MCP. Two agent classes: primary agents (own the main conversation, cycled with Tab / `switch_agent`) and subagents. Dynamic workflow○ no

opencode's multi-agent story is configuration plus tool invocation, not scripting. Positioning

Kimi Code CLI is a direct Claude Code / Codex CLI competitor from a Chinese frontier lab, aimed at developers who want a fast, fully open-source terminal agent that can be pointed at Moonshot's cheap-and-large Kimi models or at any other provider. Its differentiating bet is autonomy-at-scale rather than a novel action model: swarm fan-out to 128 subagents, goal mode that runs to a verifiable finish line, background tasks and in-session cron are all shipped as ordinary tools the model can call, which is well past what most coding CLIs expose. pi

The unopinionated harness: a thin four-tool core, everything else an extension

Identity & status

Pi is a minimalist, terminal-first AI coding agent CLI built by Mario Zechner (creator of libGDX/RoboVM), originally hosted at github.com/badlogic/pi-mono and now canonically at github.com/earendil-works/pi (badlogic/pi-mono redirects there). It is explicitly NOT Inflection's Pi chatbot and NOT Raspberry Pi. The project is a monorepo ("pi-mono") containing the agent CLI (@earendil-works/pi-coding-agent, formerly @mariozechner/pi), a unified multi-provider LLM API (pi-ai), an agent runtime (pi-agent-core), and a custom differential-rendering terminal UI library (pi-tui), plus a separate pi-chat package for Slack/chat integration and a pi-skills companion repo. MIT licensed, fully open source.

As of July 2026: actively developed, ~39K+ GitHub stars per trending coverage, npm package @mariozechner/pi / @earendil-works/pi-coding-agent; install via npm or https://pi.dev/install.sh; self-update via `pi update --self --force`, version-checked against https://pi.dev/api/latest-version at startup.

Positioning

pi is the "unopinionated harness" pole of the coding-agent landscape: where Claude Code and Codex CLI bake in MCP, sub-agents, plan mode and permission prompts, pi ships a deliberately thin four-tool core and pushes every one of those features into a TypeScript extension/package layer — "Adapt Pi to your workflows, not the other way around." It is for developers who want to own and reshape their harness (and who are comfortable running an unsandboxed agent inside their own container), not for teams wanting a batteries-included, governed enterprise product. Its bet is that the harness will commoditize while the customization surface and a community package registry become the real moat — a bet that at 79.7K stars and 5,400+ community packages is currently paying off, at the explicit cost of shipping no runtime safety boundary and no long-running/autonomous operation story of its own.

In depth

pi (formally the "Pi Coding Agent", npm `@earendil-works/pi-coding-agent`) is a minimal terminal coding-agent harness created by Mario Zechner (badlogic, of libGDX fame), now published under the earendil-works GitHub org at github.com/earendil-works/pi (the old badlogic/pi-mono redirects there). It is a TypeScript monorepo of four published packages: pi-ai (unified multi-provider LLM API), pi-agent-core (agent loop / tool calling / state), pi-coding-agent (the CLI), and pi-tui (differential-rendering terminal UI). The GitHub API reports 79,674 stars and 9,809 forks as of 2026-07-28, with the repo created 2025-08-09, last pushed 2026-07-28, and latest release v0.82.1 published 2026-07-25 (adding Claude Opus 5 support across Anthropic and Bedrock) — this is an extremely fast-moving project, and the dossier's "~39K stars" figure is badly stale. The design thesis is stated on pi.dev as an explicit "What we didn't build" list: no MCP, no sub-agents, no permission popups, no plan mode, no built-in to-dos, no background bash. What it does ship is a four-tool core (read/write/edit/bash, plus grep/find/ls), 15+ providers with OAuth subscription login, tree-structured JSONL sessions with branching and compaction, Agent Skills-standard skills, AGENTS.md/SYSTEM.md context engineering, and four operating modes (interactive TUI, print, JSON event stream, JSON-RPC over stdio) plus an embeddable SDK. The critical thing the sweep dossier under-weighted is that pi has since grown a first-class package system — `pi install npm:<pkg>` / `git:` / local path, with `pi remove|list|update` — and a public gallery at pi.dev/packages listing 5,400+ npm packages tagged `pi-package`, so nearly every "missing" feature (MCP client, sub-agents, persistent memory, Telegram, web search, permission enforcement) exists as a one-command community install. Extensions get a deep TypeScript hook API (`pi.registerTool`, `pi.on("tool_call")` for interception/mutation, custom TUI, slash commands, `pi.appendEntry` session persistence) and can even replace the built-in tools outright. Everything is MIT-licensed, runs entirely on the user's machine with their own API keys, and has no vendor-hosted data plane.

Memory◐ partial

Positioning

DeepSeek's bet is that the harness itself — not the model — is the product: "an open harness that runs anyone's model is a bid to own the workspace rather than the engine" (TNW). The launch positions it directly against Claude Code (VentureBeat headline: "launches as open source rival to Claude Code") and frames US rivals as "hard-coding their products" against an open, swappable stack. Two structural decisions define it. First, radical modularity: Cordis plugins contribute services, typed events, and reversible effects to a shared context — the model adapter, the tool registry, the session log, and even the agent loop itself are plugins, so every part is replaceable from configuration ("there is no privileged core to patch", docs/architecture.md). Second, traceability as a feature: an append-only session event log records everything the model sees — system prompts, reasoning, tool calls, subagent scheduling, context injections — and resume, fork, search, and replay all operate on that one stream; HN commenters called the trajectory view the launch's killer feature. The plugin-model comparison with Ava cuts both ways: both make every capability a mountable module and both speak the Agent Skills standard — but dsh's plugin surface reaches deeper (its plugins can replace the agent loop and persist the log; Ava's plugins extend the ava.* SDK namespace and skill set), while Ava's plugin layer is one tier of a minimal core (one tool, one namespace, minimal by design) where dsh's is the product's entire constitution. 殊途同归 in capability grammar; opposite bets in where complexity lives.

In depth

A running dsh is a plugin tree composed at boot from ordered layers: a profile (a named composition under $DSH_HOME/profiles; web and headless ship as templates) stacks bundles (patch-layer distribution units; dsh-base is the first layer of every profile: model adapters, tools, persistence, sandbox + approval policy, settings, credentials, telemetry), then the profile's cordis.patch.yml, the home-level one, and --patch overlays — any row the boot prints under dsh --dump-config can be replaced by a patch. A step is one model request plus the tools it calls; a turn is zero or more steps; extension points are typed events and three waterfall seams (agent/pre-step, agent/request, llm/stream, the tools/* gates) whose listeners must call next() to delegate. The session log is the single source of truth: "Model-visible means logged" is a runtime invariant — anything reaching a model request must be reconstructable from the log, persisted append-only to JSONL or SQLite with torn-tail recovery, and compaction (automatic pressure plus a human /compact command) summarizes older spans. Official runtime modes: Standard (full multi-tool agent), Code mode (all Standard capabilities through a Code Mode SDK so the model composes multi-step work in one TypeScript program), Minimal (two tools — persistent bash + str_replace_editor — for benchmarking models), and Creator (runtime inspection, in-memory plugin experiments, preset authoring). Subagents run behind one ctx.subagents seam with seven provider packages — including first-party backends that delegate a turn to a real Claude Code or Codex process. The generated tool catalog (docs/tool-catalog.md) is boot-verified: a CI gate boots every tool plugin on a real context and reads ctx.tools.schemas(), so a shipped tool cannot be silently undocumented.

Dimension reviews

Action model

The real spectrum is three-step, not binary: primary code-act — Ava alone (no tool schemas; the model writes Python and ava.* is the capability surface); optional code-act — Codex (an experimental Code Mode subsystem in source, server-side enableable), OpenClaw (auto default), Hermes (on by default, seven tool families only), plain multi-tool — Claude Code (Workflow scripts orchestrate subagents but never touch the capability surface), Hermes (on by default, seven tool families only), DeepSeek Harness (a first-class native|code|both registry mode — under code, one run_code transport plus a generated TypeScript/Python SDK; Cloudflare Code Mode lineage, worker-thread isolated); plain multi-tool — Claude Code (Workflow scripts orchestrate subagents but never touch the capability surface), opencode (shipping release; its CodeModeTool is flag-gated experimental, off by default), pi, Grok Build, Kimi Code. The industry is retrofitting code-act as an escape hatch; Ava's divergence is making it the only entrance.

Skills

Ten for ten: Agent Skills (SKILL.md) has gone from an Anthropic product feature to a de-facto industry standard (agentskills.io) — the most unexpected uniformity in this study. Differences live in loading strategy (progressive disclosure vs load-at-start) and self-authoring — Claude Code, Hermes and Ava let the agent write its own skills; DeepSeek Harness reads the same SKILL.md roots (.agents/skills, ~/.agents/skills) with model/user invocation policies. Ava installs unmodified standard skills as of 2026-07-29.

MCP

Broad support, different roles: OpenClaw, Hermes, Codex — and, since 2026-07-29, Ava — act as both client and server; opencode, Kimi Code, Grok Build and DeepSeek Harness are client-only (dsh bridges stdio + streamable-http servers as mcp__<server>__<tool> tools — its three default-off memory-server reference configs make cross-session memory the canonical third-party-MCP case); pi markets not doing MCP (CLI tools + READMEs instead). Server mode is becoming the watershed for personal agents — it lets the agent itself be driven by other agents.

Memory

Three paradigms coexist: human-authored instruction files (AGENTS.md/CLAUDE.md family — pi, opencode, Kimi Code), agent-written memory files (Hermes's MEMORY.md/USER.md, OpenClaw's journal workspace, Codex's native memories — off by default), and a shared retrieval pool (Ava's cluster-wide markdown pool + Memory Steward: one agent writes, the whole fleet searches — unique in the set). DeepSeek Harness's memory of record is its append-only session event log — fork, resume, search and replay derive from one stream — but it ships no built-in cross-session store, delegating that role to third-party MCP servers, which rates partial. Under a uniform yardstick (agent-written persistence ships = yes; default-off doesn't dock), the first five rate yes; Ava's plugin-layer provenance stays in the detail.

Self-evolution

Everyone rates partial or better, but depth varies enormously. Binary self-update (pi, opencode, Codex, Grok Build, Kimi Code) is the shallowest layer; skills-and-memory self-authoring (Hermes, OpenClaw, Claude Code) the middle; only Ava makes "upgrade your own runtime" one operator command — ava cluster update drains the cluster and rolls merged main (the old ava.self.update() SDK call was removed 2026-08), and agents open PRs against their own source. DeepSeek Harness adds a third texture: the model can inspect and temporarily extend its own live runtime (cordis_inspect/mount/unmount) but cannot upgrade its installed code.

Multi-agent

The coding camp embraced subagents wholesale (Codex Multi-Agent V2, Kimi's swarms, Claude Code's four orchestration tiers), but mostly as context isolation inside one process. DeepSeek Harness runs the richest single-process subagent seam — seven providers, one-shot and continuable children, session trees with cold resume, and first-party backends that delegate a turn to a real Claude Code or Codex process. Process-level, cross-machine, resurrectable fleet primitives — spawn/fork/terminate/restart/resurrect over a decaying peer graph, plus a per-agent notice queue and a shared task registry — exist only in Ava (and OpenClaw approaches it via multi-persona routing); pi makes "no subagents" a stance. Runtime LLM-decided decomposition is now consensus.

Dynamic workflow

The scarcest cell on the board. Under a strict bar — the model writes an orchestration script at runtime, executed with real control flow — only Claude Code, Ava, OpenClaw and DeepSeek Harness clear it; pi's pi-crew .dwf.ts earns a partial. Codex, Kimi and Grok Build orchestrate through parameterized built-in tools, and Hermes's docs state outright there is no generated orchestration script. Among the four, the runtimes differ: Claude Code ships a dedicated background runtime (1,000 agents / 16 concurrent), DeepSeek Harness runs the model-written script in a worker thread (parallel/pipeline hooks, per-run agent caps), OpenClaw runs scripts in a sandboxed guest (16 pending-call cap), Ava has no separate runtime at all — the script runs inside the agent's own execute_code turn, and long runs re-enter as a per-wave state machine with checkpoint-based collection (workers end silently; the script picks its wake-ups).

Goal mode

Far more widespread than expected: six yes (Claude Code, Hermes, Codex, Kimi Code, DeepSeek Harness — autonomous goal rounds with authority checks, completion model-reported by explicit design, no evaluator), three partial (pi — lives in extensions; OpenClaw — no evaluator; Grok Build — self-checked checklist), one explicit no (opencode closed the feature request as not-planned), and Ava now honest-rated partial (user ruling 2026-08-13): the peer-agent-judge mechanism ships but has not yet been exercised on real goals — it sits in the matrix as a candidate, not a verified strength. The real differentiation is who judges: Claude Code (independent Haiku evaluator), Hermes (five-field completion contracts + auxiliary judge) and Ava (a peer-agent judge that inspects the artifact, never the worker's claim) use independent evaluation; Codex, Kimi and DeepSeek Harness self-assess against verifiable criteria. Ava's distinction: its judge is a full agent with tools — it can run the checks itself rather than read a transcript.

Model routing

Provider neutrality is table stakes in the open camp (pi 15+ providers, opencode 75+, Hermes 300+ models, DeepSeek Harness catalog providers plus custom OpenAI-compatible endpoints); the closed camp locks to its own family (Claude Code is Anthropic-only). Part five · Where Ava stands

The bet: code is the only tool an agent needs

  • One tool, period. Every capability is a Python call under ava.*; the model's only tool is execute_code. Of the ten agents surveyed, Ava is the only one whose sole action model is code itself — no dispatch schemas, no escape hell.
  • A fleet, not a session. ava.agents.spawn / fork / resurrect are process-level primitives across machines. Orchestration is a Python script the agent writes at runtime — plain Python with real control flow, not a DSL, not YAML, no external scheduler. Workers end silently; the script decides its own checkpoints.
  • It updates itself. ava cluster update rolls the whole cluster: drain live agents, pull, migrate the DB, restart. Agents author their own skills and file PRs against their own source.
  • You own the data plane. Each cluster runs its own Postgres + Redis under its home directory, auth always on, Apache-2.0. Nothing phones home.
  • Always on, cheaply. Watchers (at / cron / launch), heartbeats and OS-scheduled jobs make agents persistent processes — and hibernation reclaims an idle agent's whole process (~450s threshold, sub-second revival), so a big fleet idles nearly free.
  • Any model per task — chosen by the agent. Eight provider families, routed per spawn via config_overlay. Deliberately no mid-run auto-fallback: model choice is the agent's decision, not an opaque router's.
